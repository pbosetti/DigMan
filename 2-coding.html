CMake Script

Steps:

  • project setup
  • define common switches
  • define headers and library locations
  • define targets
  • define install behavior
cmake_minimum_required(VERSION 3.9)
set(CMAKE_C_COMPILER "clang")
# Set project name, version, and language
project(C-CNC VERSION 0.0.1 LANGUAGES C)
# Set common compile options and preprocessor definitions
add_compile_options(-std=gnu11 -fPIC)
add_definitions(-D_GNU_SOURCE)
# Define the list of source files
set(SOURCE_DIR ${CMAKE_HOME_DIRECTORY}/src) #set a variable
file(GLOB LIB_SOURCES "${SOURCE_DIR}/*.c") #put into LIB_SOURCES the globbed list
# Parametrically create some file from template
configure_file(
  ${SOURCE_DIR}/version.h.in
  ${SOURCE_DIR}/version.h
)
# define header directories
include_directories(
  ${CMAKE_HOME_DIRECTORY}/machine/src
)

# Define TARGETS, i.e. output objects
# Library target:
add_library(ccnclib STATIC ${LIB_SOURCES})
target_link_libraries(ccnclib machine)
# Main executable
add_executable(ccnc ${SOURCE_DIR}/main/ccnc.c)
add_dependencies(ccnc ccnclib)
target_link_libraries(ccnc ccnclib)

# INSTALL
set(CMAKE_INSTALL_PREFIX ${CMAKE_HOME_DIRECTORY})
install(TARGETS ccnclib ccnc
  RUNTIME DESTINATION bin
  LIBRARY DESTINATION lib
  ARCHIVE DESTINATION lib
)

Stack vs. Heap memory

FIFO access (fast)

Typ. ~8 Mb capacity per thread (check with command ulimit -s)

Random access (slower)

Virtually unlimited

Tricky Pointers

  • Standard variables are defined on the stack memory
  • You get the pointer to variable var with &var
  • You get the value of pointer var_p with *var_p
  • Arrays are pointers to their first element, but stack arrays have a limited maximum size (system dependent)
  • Variables on stack are eliminated from memory on exiting from local scope

Tricky Pointers

  • Pointers requiring large (or dynamic) memory can be defined on the heap memory
  • You allocate a pointer on the heap with the malloc() family of functions
  • malloc’d variables are not freed upon exiting from local scope
  • For every malloc() you need one free(), or you have a memory leak ☠️☠️☠️

Ways for returning an array in C

  • Use malloc() in the caller and pass the pointer as an inout argument (easier)
  • Call malloc() inside the function and return that pointer (easy, but you cannot return anything else, like error status)
  • Pass a double pointer to the callee as an inout argument, use malloc() inside the function (not so easy, but you can also return a status value)

Memory leaks

MQTT basics

MQ Telemetry Transport protocol — using C language and Mosquitto broker

MQTT protocol

  • MQTT stands for Message Queue Telemetry Transport
  • Actually, there is no queue but rather a publish-subscribe architecture
  • The protocol is lightweight: it minimizes the overhead of messages
  • It is about 100 times faster than REST HTTP messaging (in terms of maximum msg/s)
  • It is not the fastest protocol (ZeroMQ is faster), but it is simple to implement and well balanced

MQTT protocol

  • In MQTT there are 3 different roles: publisher, subscriber, broker
    • The publisher is the information producer (to be implemented)
    • The subscriber is the information consumer (to be implemented)
    • The broker is a server that relays publisher messages to (possibly many) subscribers (already available)
  • Messages are published under topics
  • Topics are arranged hierarchically: ccnc/x/pos, ccnc/y/vel

MQTT protocol

Subscribers can subscribe to more than one topic, possibly also using wildcards (+ or #):

  • ccnc/+/pos means any single word in between ccnc and pos (as ccnc/x/pos and ccnc/y/pos, but not ccnc/x/nominal/pos)
  • ccnc/#/pos means anything (including multiple branches) under ccnc and ending with /pos

MQTT protocol

  • Publishers can publish messages to many different topics, but one at a time (no wildcards!)
  • A message is also called a payload: any sequence of bytes, up to a maximum 268435456 bytes (\(2^{28}\), ~260 Mb)
  • Bigger payloads need to be split (or compressed)
  • Messages are assigned with a quality of service level (QoS) and with an optional retain flag

MQTT protocol

The QoS level states the reliability of a message:

  • QoS 0: a message is delivered at most once
  • QoS 1: a message is delivered at least once
  • QoS 2: a message is delivered exactly once

QoS 0 is “fire-and-forget”: less reliable but with minimum information exchange. QoS 2 has a delivery confirmation: 100% reliable, but slower

MQTT protocol

  • The retain flag, when set, instructs the broker to deliver the message to any subscriber connecting in the future
    • It is a kind of “last known value” clause
  • There are also last will and testament (LWT) messages: these are messages delivered as soon as the broker detects that the client has disconnected
  • Note: the roles of publisher and subscriber are semantic: any given process can simultaneously act as publisher and subscriber, if needed. Both are clients of the broker server

MQTT Applications

  • There are many available broker services, like mosquitto, Paho, HiveMQ, Mosca, EMQ X, VerneMQ.
  • As well, there are many libraries for implementing MQTT clients (pub+sub) in virtually any known programming language
  • We will refer to mosquitto (the broker) and libmosquitto (the C library)

MQTT Broker

The mosquitto config file (mosquitto.conf) typically contains at minimum:

allow_anonymous true
listener 1883
protocol mqtt

This accepts any connection. In production, you might want to require passwords and encrypted connections.

MQTT library

  • Documentation is on https://mosquitto.org/api
  • The library namespace is mosqpp, the main class is mosquittopp
  • Typical sequence of operation:
    • Start > library init > client init > client connect > set callbacks > loop { publish messages & update sockets } > free resources > stop
  • Callbacks are methods automatically called on given events (e.g. successful connection, receiving subscribed message, …)

MQTT library

  • Library init: mosqpp::lib_init()
    • It simply MUST be called before any other mosquitto call
  • Library cleanup: mosqpp::lib_cleanup() (in destructor)

MQTT library

  • Client init: auto mqt = mosquittopp(id, clean)
    • id: can be a name (useful for debugging, only visible to the broker)
    • clean: ask the broker to delete all messages and subscriptions on disconnect
  • Typically, you derive a class from mosquittopp

MQTT library

  • Client connect: mosquittopp::connect(broker_addr, broker_port, keepalive)
    • Connect the object to a given broker host and port
    • The broker pings the client (if no messages arrive) every keepalive seconds to verify if it is connected

MQTT library

  • Implement callbacks: mosquittopp::on_message(const struct mosquitto_message *message) (et similia)
    • Object calls on_message each time a message is received

MQTT library

All network operations are just scheduled by subscribe and publish functions. They are actually performed in two alternative ways:

  • By repeatedly/cyclically calling mosquittopp::loop() (preferred if you already have a loop)
  • By starting a parallel thread that iteratively calls mosquittopp::loop(): this is done by calling mosquittopp::loop_start() just after mosquittopp::connect()

MQTT library

  • To schedule the publishing of a message, use mosquittopp::publish(mid, topic, len, payload, qos, retain)
    • The payload is any sequence of len bytes (a string or a binary object)
    • The message ID mid is typically NULL

MQTT library

  • When a message is received, the on_message callback is executed
  • It gets the message as a struct mosquitto_message, which contains:
    • Message ID (if any), topic, payload, payload length, QoS level, retain flag.
  • It does not contain any info on the publisher!
  • The subscriber HAS NO WAY for identifying the publisher (unless it is written in the payload or topic)

MQTT library

When done, you should, in this order:

  1. Unsubscribe all subscriptions
  2. Call mosquittopp::loop or mosquittopp::loop_stop
  3. Disconnect from broker
  4. Call mosqpp::lib_cleanup

  • MQTT explorer is a useful graphical tool for tapping into MQTT dataflows: http://mqtt-explorer.com

Cargo Cult

If it looks like a plane, that doesn’t necessarily mean it can fly. What you definitely don’t want to do in engineering!

Cargo cult in anthropology

  • A cargo cult is a belief system, in which adherents perform rituals which they believe will cause a more technologically advanced society to deliver goods
  • Many examples in remote Pacific islands, where inhabitants replicate US army “rituals” in the hope of calling a cargo delivery

Cargo Cult programming/engineering

Typical pattern:

  • You don’t know how to solve a problem
  • You type “How to do something in my language?” in Google (or ChatGPT!)
  • You end up on Stackoverflow (or similar sites) or get an AI-generated code
  • You copy and paste the first solution, which you cannot fully understand but it seems to work

Why is that a bad habit?

  • At best, it messes up your coding style (e.g. using variableNames rather than variable_names)
  • You may look amateur and naïve to those who read your code (among them, your prospective employer!)
  • Foremost, you are losing control on your code, which may work fine in the stackoverflow/AI example, but much probably does hidden nasty things once embedded in your code
  • Additionally, your problem understanding does not improve

Doesn’t happen only when you code

  • There are many examples of cargo cult engineering as well
  • Each time you accept an existing solution just because it works in another emplacement, and without fully understanding it, you are a cargo cultist
  • Always question any solution; ask why; do not accept any solution that you cannot fully understand, at least in its outer structure (input/output relations, interfaces, specifications)

Tool radius compensation

  • G-code standard supports a feature for offsetting the tool trajectory to the left or to the right of the trajectory by an amount equal to the tool radius
  • This is only affecting the X-Y projection of the trajectory, Z values remain unchanged
  • The TRC is set to the left with G41, to the right with G42 and is disabled with G40
  • TRC is fully active at the end of the current block

Tool radius compensation

  • TRC offsets the tool center path (programmed points) according to G41/G42
  • New target points are calculated for each block on the basis of the offset intersection with the next block (arc or line)
  • Disabled for rapid motions

Line-Line case

We need to calculate the point \(D\):

  1. Given the line equation \(y = ax + b\), we need to calculate the equation of the offset line(s)
  2. Calculate \(D\) as intercept between the two offset lines

Line-Line case

  • Given \(y = ax + b\), the equation of the offset line is \(y = ax + b - v\)
  • Being \(a = u/r\), it follows that: \(v = \sqrt{u^2 + r^2} = r\sqrt{a^2 + 1}\)
  • So, \(y = ax + b \pm r\sqrt{a^2 + 1}\)
  • The sign depends on G41/G42 and on the path direction

Line-Line case

Intersection \(D\) between

\(y = a_1 x + b_1 - v_1 = a_1 x + b_{o,1}\)

and

\(y = a_2 x + b_2 - v_2 = a_2 x + b_{o,2}\)

has coordinates:

\[(x_i, y_i) = \left(\frac{b_{o,2} - b_{o,1}}{a_1 - a_2}, \frac{b_{o,1}a_2 - b_{o,2}a_1}{a_2 - a_1}\right)\]

Line-Line case

  • Exception: when two segments are collinear (\(a = a_1 = a_2\)), the intercept is undefined
  • The new intersection node is set at an offset \(r\) perpendicular to the segments

\[C = \begin{cases} (0, -r), & \text{when } a = 0 \\ r(s, -s/a) \text{ with } s = \frac{a}{|a|}\sqrt{\frac{a^2}{1 + a^2}}, & \text{otherwise} \end{cases}\]
